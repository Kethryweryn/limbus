# Tests

Intégration (`tests/integration/`) : l'application compilée tourne contre une base PostgreSQL jetable, dont le nom doit contenir « test » car elle est vidée. Le scénario : deux organisatrices, Alice et Bob, et une co-organisatrice ; on vérifie qu'Alice n'atteint rien du jeu de Bob, avec un témoin positif à chaque fois. Un test lit une réponse avec le type de sa route : `bodyOf<ApiResponse<'/api/…'>>(response)`, `WithField` pour une réponse à plusieurs formes, `errorMessage` et `invalidPaths` pour un refus (`tests/integration/api.ts`). Lancement : `npm run build && TEST_DATABASE_URL=postgresql://…/limbus_test npm run test:integration`. En local sous Windows, il faut passer par un conteneur Linux.

Bout en bout : Playwright (`tests/e2e/`), dans Chromium, contre l'application compilée et la même base de test : connexion, déconnexion, 403, accès au compte (mot de passe oublié, inscription libre, confirmation, changement d'adresse et de mot de passe, export et effacement), écriture du jeu (création, renommage, suppression de chaque élément, partage d'un jeu), page publique, legs, inscription sur invitation, actions de l'équipe sur les inscriptions, compte, administration, participants, présence, et les parcours (casting, trombinoscopes, envoi des documents, paiements, hors ligne, modification, annulation et report d'une session, présence, timeline de session, qualité du questionnaire), assistants d’IA (page « Autoriser », assistants connectés, réglage du partage), nouveautés. Les parcours partagent le « Jeu des parcours » préparé par `globalSetup.ts` ; chaque test y crée sa session (`parcoursSession`) et ouvre la session par cookie (`signIn`), car l'écran de connexion limite à 10 tentatives par email (ADR-0037). Les fichiers de tests tournent sur trois navigateurs en parallèle, avec un seul faux serveur d'emails (ADR-0059) : un test lit ses emails par `openMailbox` et les adresse à une personne qui lui est propre (`parcoursPerson`), et ne change aucun réglage global. Lancement : `npm run build && TEST_DATABASE_URL=… npm run test:e2e`. Sous Windows, passer par l'image `mcr.microsoft.com/playwright:v<version>-noble` (même version que `@playwright/test`). Attendre `networkidle` avant de remplir un formulaire : avant l'hydratation, le clic le soumet nativement.

Tests à écrire (ADR-0079) : un écran, une action ou une route ajoutés ou changés ont leurs tests Playwright sur quatre axes : actions (chaque bouton, filtre, recherche, lien, onglet, page), erreurs de saisie (message attendu, rien d'enregistré), droits (co-organisatrice, organisatrice sans accès, participante), hors ligne (relecture sans réseau, modification envoyée au retour du réseau). Un axe qui ne s'applique pas est écrit dans l'US, avec sa raison. Les outils communs sont dans `tests/e2e/helpers.ts` (`orgaGame`, `orgaSession`, `gamePerson`, `gameCharacter`, `castSession`, `cardByTitle`, `blockWith`) : un test crée ses données dans un jeu qui lui est propre. Après une navigation dans l'application, attendre le titre principal (`h1`) de la page arrivée, car la page quittée reste affichée tant que la suivante charge.

Dépendances : Dependabot ouvre chaque lundi une PR groupée (mineures et correctifs) et une PR par version majeure. La CI les valide ; les fusionner les déploie.

Unitaires : Vitest (`tests/`). `tests/setup.ts` recrée les auto-imports Nitro (`createError`, `getHeader`, `useRuntimeConfig`…) et remplace Prisma par un objet vide. Dans un test, on lui assigne les méthodes nécessaires (voir `tests/server/auth.test.ts`). `h3` est fixé en v1 en devDependency pour correspondre à Nitro.
