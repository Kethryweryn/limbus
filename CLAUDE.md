# Limbus

Outil d'organisation de GN (Nuxt 4, Nuxt UI 4, Prisma 7 / PostgreSQL). Contexte produit : README.md ; installation, variables et commandes : doc/developpement.md. Le code et l'interface sont en français.

## Documentation (`doc/`)

Toute évolution suit le cycle décrit dans `doc/README.md` : fiche `doc/todo/` → `SPEC-NNN` → epics et `US-NNN` → archive.

- Une nouvelle idée ou demande de fonctionnalité devient d'abord une fiche todo (modèles dans `doc/modeles/`).
- Toute décision technique (modèle de données, algorithme, bibliothèque, sécurité) fait l'objet d'un ADR dans `doc/adr/`. On ne supprime pas un ADR, on le remplace.
- Les commits d'implémentation citent l'US ; l'US et l'index sont mis à jour dans le même commit. Exception : un correctif ou un nettoyage sans changement de comportement (revue de code, recommandation d'une revue, dépendances) n'a pas d'US ; il cite sa source (fiche, revue, PR).
- Avant de travailler sur une fonctionnalité, lire sa spec et les ADR liés. Chaque dossier a un index `README.md` : le tenir à jour.

## Nouveautés

Une PR qui change ce qu'une personne voit ou peut faire, correction d'un défaut rencontré comprise, ajoute sa note dans `nouveautes/` : un fichier JSON (`type` : `nouveau`, `modifie`, `corrige` ou `retire` ; `titre` ; `texte`), en français, pour les personnes qui utilisent Limbus, sans vocabulaire technique, ni donnée personnelle, ni détail du serveur ou d'une faille. La revue de code le vérifie. On ne renomme pas une note : sa date vient du commit qui l'a ajoutée (SPEC-017, ADR-0065).

## Jeux de test

Une fonctionnalité qui ajoute une donnée à essayer complète `prisma/seed/` et `doc/jeux-de-test.md` dans la même PR (ADR-0066). `tests/integration/seed.test.ts` lance le script : il casse la CI s'il ne suit plus le schéma. Le déploiement ne le lance jamais ; le rechargement en production se fait seulement à la demande de l'utilisatrice, car il remplace les trois jeux.

## Avant de considérer un changement terminé

Avant chaque push, correction de revue comprise :

- `npm run lint`, `npm run typecheck` et `npm test` passent ; lire leur résultat.
- Les tests liés au changement passent : relever les écrans, routes et utilitaires touchés, puis jouer les fichiers Playwright et d'intégration qui les couvrent, pas seulement les tests ajoutés. Sous Windows, le build échoue au prérendu : passer par le conteneur Linux (voir Tests). Si ces tests ne peuvent pas tourner, le dire et demander avant de pousser.

La CI de la PR joue ensuite la suite complète (ADR-0023) : inutile de la relancer entière en local.

Revue de code : chaque PR passe par `/code-review`. Tout constat se corrige, nettoyages compris (réutilisation, simplification, efficacité), même dans du code antérieur à la PR. Aucun constat n'est écarté sans l'accord explicite de l'utilisatrice ; un constat jugé faux lui est présenté avec sa raison.

On ne pousse jamais directement sur `main` (ADR-0017) : chaque chantier a sa branche (`us/…`, `doc/…`, `fix/…`, `deps/…`) et sa pull request, qui cite ses US, specs et ADR. On fusionne en squash une PR dont la CI est verte ; GitHub l'impose, et exige une branche à jour avec `main` (ADR-0023). La CI de la PR construit l'application dans un conteneur Debian 12 + Node 24 (comme le serveur), la teste et archive ce build ; la seule vérification exigée est « Verdict CI ». La fusion dans `main` ne relance pas la CI : **le build testé est déployé aussitôt en production** (job `deploy`, qui l'envoie à `deploy.sh <sha>` sur le serveur ; lancé à la main, `deploy.sh` reconstruit sur place). Fusionner une PR est donc une mise en production. Une PR qui ne touche que `doc/` ou les `*.md` de la racine passe sa CI sans rien exécuter et ne déploie rien (ADR-0022, ADR-0023). Si aucune archive testée ne correspond à `main` (archive expirée…), lancer le workflow CI à la main sur `main` : il construit, teste et déploie. Une migration ne doit pas casser le build encore en service pendant le déploiement : la CI refuse suppressions, renommages, `SET NOT NULL` et changements de type, sauf commentaire `-- deploiement-incompatible : <raison>` (ADR-0024).

## Sécurité des routes API

- Toute route sous `server/api` commence par `requireUser(event)` (ou `requireAdmin`), sauf les routes volontairement publiques : `auth/*`, `invitations/[token]` et `public/*`. Il n'y a qu'un rôle global, administratrice ou non : les droits sur un jeu viennent de sa propriété ou de son partage (ADR-0038). `requireUser` refuse un compte désactivé et un compte dont l'adresse n'est pas confirmée ; seules `auth/me`, la déconnexion et le renvoi du lien passent `allowUnconfirmed` (ADR-0039).
- Espace « Je participe » (`server/api/me/*`) : tout part des fiches participant rattachées au compte (`Participant.userId`, `myParticipantIds`), jamais d'un identifiant de jeu ; une ressource d'une autre fiche répond 404 (ADR-0041). Une fiche suit le compte confirmé de son adresse : toute création ou modification de son email recalcule `userId` (`accountIdForEmail`). Ses coordonnées (nom, téléphone, contact d'urgence, allergies) viennent alors du compte : `syncProfileToParticipants` les recopie sur ses fiches et inscriptions, et l'équipe ne les modifie plus (ADR-0042).
- Toute donnée rattachée à un jeu est filtrée par accès au jeu :
  - `requireGameAccess(event, gameId)` pour une ressource précise ;
  - `requireSessionAccess(event, id)` pour une session ;
  - `gameScopedWhere` / `accessibleGameIds` pour les listes.
- Quand une modification change le `gameId` d'une ressource, vérifier l'accès au jeu cible aussi. Les références vers d'autres entités (factions, lieu, participants, personnages) doivent appartenir au même jeu.
- Corps de requête : toujours valider avec un schéma zod de `server/utils/schemas.ts` via `readZodBody`.
- Le JWT ne porte que l'`id` et la version de session `v` : rôle et email sont relus en base à chaque requête, et un jeton dont `v` ne correspond plus à `User.sessionVersion` est refusé. Pour déconnecter un compte partout (changement de mot de passe…), appeler `revokeUserSessions`.
- Données personnelles des participants : la suppression passe par `eraseParticipant` (photos et fichiers compris), l'export par `exportParticipantData`, limité aux jeux de l'organisateur. Toute nouvelle donnée liée à un participant doit être couverte par ces deux fonctions (`server/utils/participantPrivacy.ts`). Un formulaire public pas encore confirmé (`RegistrationRequest`) n'est pas rattaché à une fiche : il ne crée rien chez l'équipe et disparaît à la confirmation ou au bout de 7 jours (ADR-0046). Une décision de sélection (retenue, en attente, non retenue) ne se voit côté personne qu'une fois annoncée : toute vue de la personne lit son statut par `announcedRegistrationStatus` (ADR-0047). Côté compte, `exportAccountData` et `deleteOwnAccount` (`server/utils/accountDeletion.ts`) couvrent le compte et ses fiches rattachées : toute nouvelle donnée du compte y entre aussi (ADR-0043).
- Toute nouvelle donnée personnelle, tout nouveau destinataire et toute nouvelle durée de conservation apparaissent dans la politique de confidentialité (`pages/confidentialite.vue`, durées dans `utils/legal.ts`). Un changement de fond des conditions d'utilisation ou de la politique change `TERMS_VERSION` : chaque compte les accepte de nouveau (ADR-0055).
- Les fichiers uploadés sont servis par des routes qui vérifient les droits, jamais en statique. On vérifie le type réel (signature) et on renomme avec un UUID.
- Fichiers téléversés (`server/utils/uploads.ts`) : tout nouveau téléversement vérifie `assertStorageQuota` (plafond de la propriétaire du jeu) et enregistre la taille du fichier (ADR-0039). Toute modification ou suppression qui retire une référence à une photo ou à un RIB appelle ensuite `deleteUnusedUploads` (relever les URL avec `collectUploadUrls` avant une suppression). Un fichier destiné à un participant part en pièce jointe, jamais en lien vers l'API ; une personne dont la fiche est rattachée à un compte le retrouve aussi dans son espace, par une route `me/*` qui vérifie le rattachement (ADR-0041). Chaque envoi garde sa copie (PDF et contenu lisible) sur sa ligne `SessionDocumentDelivery`, comptée dans le stockage de la propriétaire sans bloquer l'envoi, et effacée après la session par `purgeExpiredCopies` (ADR-0044) : un nouvel envoi passe par `sendToEach` et fournit ses copies. Une URL de fichier téléversé reçue dans un corps de requête doit désigner un fichier du même jeu : `assertGameUploads`.
- URL saisies par les utilisateurs : schémas `externalUrl` / `uploadOrExternalUrl` (http(s) ou fichier téléversé uniquement), sinon un `javascript:` s'exécuterait dans un lien ou une iframe. Seul YouTube est intégré en iframe (`youtubeEmbedUrl`). Le serveur ne télécharge une ressource externe que via `fetchPublicResource` (`fetchPublicImage` pour une photo) : hôte public, délai et taille bornés.
- Une ressource ne change jamais de jeu (`assertSameGame`).
- Les liens absolus (emails, PDF) passent par `absoluteAppUrl()`, jamais par les en-têtes Host.
- L'IP client pour le rate limit est la dernière entrée de `X-Forwarded-For`, ajoutée par Apache (voir `clientIp`).
- Les écritures sous `/api/` doivent venir de Limbus : `server/middleware/origin.ts` refuse un POST, PUT, PATCH ou DELETE venu d'un autre site ou sans `Sec-Fetch-Site`, `Origin` ni `Referer` (ADR-0053). Un test ou un outil qui écrit envoie l'un d'eux. Le cookie de connexion s'appelle `__Host-limbus_token`. La CSP est posée par Nuxt Security (`nuxt.config.ts`) : une nouvelle ressource externe (script, iframe, connexion) doit y être autorisée.
- Jamais de `process.env.X` dans `nuxt.config.ts` pour un secret : la valeur serait figée en clair dans `.output` au build. `runtimeConfig` reste vide, et le code lit `useRuntimeConfig().x || process.env.X` à l'exécution.
- Toute nouvelle route ou ressource liée à un jeu doit être ajoutée à `tests/integration/isolation.test.ts`.
- Assistants d'IA (SPEC-014, ADR-0058) : `/mcp` et `/oauth/*` sont hors de `server/api`. `/mcp` n'accepte que le jeton Bearer d'un assistant, jamais le cookie, et la passerelle pose le compte et l'autorisation sur l'événement (`bindAiAuthorization`). `gameAccess` restreint alors tout aux jeux de l'autorisation, et le mode administrateur ne s'applique jamais. Un outil (`server/mcp/`) appelle les fonctions serveur, jamais l'API HTTP. Il rend une projection explicite (`select`), jamais un objet Prisma tel quel : ni coordonnées, ni allergies, ni paiements, ni fichiers, ni texte libre écrit par un participant (R8). Une écriture d'un assistant est notée au journal (`aiLog`). Le jeu et son contenu s'écrivent par `server/utils/contentWrites.ts`, les sessions (détails, équipe, casting, déroulé) par `server/utils/sessionWrites.ts`, les fiches participant par `server/utils/participantWrites.ts` et les périodes d'inscription par `server/utils/registrationPeriodWrites.ts` (décisions, tirages et formulaire ont déjà leurs fonctions communes), communs aux routes et aux outils : une règle d'écriture s'y change, pas dans une route. Un outil de modification complète les champs donnés avec la fiche actuelle et passe la version lue (`event.context.writeVersion`, contrôlée par `assertUnmodifiedSince`). Un assistant ne pose aucun lien ni fichier.

## Conventions API

- Les pages utilisent des slugs (`/games/:slug`, `/characters/:slug`). L'API qui modifie ou relie des données utilise les identifiants stables (`PUT /api/games/:id`), car un slug change avec le titre.
- Les lectures par slug sont explicites : `GET /api/games/slug/:slug` ; une route `[id]` n'accepte jamais un slug (`server/utils/sheetReads.ts` lit une fiche par l'un ou l'autre). Une page de fiche lit par son slug, puis appelle l'API par l'identifiant de ce qu'elle a lu.
- Fichiers d'API : suffixes Nitro `.get.ts`, `.post.ts`, `.put.ts`, `.delete.ts`.
- Écritures concurrentes : `assertUnmodifiedSince` (`server/utils/concurrency.ts`) ; `assertRowsVersion` pour une liste remplacée d'un bloc, dont la version est le plus récent `updatedAt` de ses lignes.

## Conventions UI

- Nuxt UI v4 : le contenu d'un `UModal` va dans le slot `#body`, sinon il s'affiche dans la page.
- Chaque page doit avoir un seul élément racine dans son template.
- TypeScript strict (ADR-0057) : tout composant et toute page sont en `<script setup lang="ts">`, sans `any` : la règle de lint (`eslint.config.mjs`) impose `lang="ts"` à tous les `.vue` et refuse tout `any` dans le dépôt, tests et scripts compris. Les appels passent par `useApiFetch`, typé par la route, et ceux d'une page publique (lien personnel, présence, invitation) par `publicFetch` ; une écriture se teste avec `isOfflineQueued`, une action passe par `useApiAction`, un état se type avec `ApiResponse`. Une page de liste lit avec `fetchOfflineList` et se relit avec `useConnectionRefresh` ; une liste sans magasin propre lit avec `useApiFetch(url, { offlineCache: true })`, car un nouveau magasin IndexedDB demande de changer la version de la base (`utils/storage.ts`).
- Hors ligne : la déconnexion efface tout ce qui est sur l'appareil (`clearOfflineData`), et la connexion d'un autre compte aussi (`claimOfflineData`). Seul un 401 renvoie à l'écran de connexion ; un 403 est un refus ponctuel.
- Hors ligne : les écritures sont mises en file (`utils/offlineSync.ts`) et rejouées avec la version lue, suppressions et sous-routes comprises (ADR-0036). Une page à consulter hors ligne lit avec `useApiFetch(url, { offlineCache: true })` (ou `useOfflineFetch` si elle est rendue côté serveur). Une modification qui porte sur une ligne sans `updatedAt` propre envoie la version de ce qu'elle a lu (`NO_VERSION` si la ligne n'existe pas). Un POST ou un DELETE sur une sous-route (envoi d'emails, génération, legs, partages…) est une action : jamais mis en file.

## Tests

Intégration (`tests/integration/`) : l'application compilée tourne contre une base PostgreSQL jetable, dont le nom doit contenir « test » car elle est vidée. Le scénario : deux organisatrices, Alice et Bob, et une co-organisatrice ; on vérifie qu'Alice n'atteint rien du jeu de Bob, avec un témoin positif à chaque fois. Un test lit une réponse avec le type de sa route : `bodyOf<ApiResponse<'/api/…'>>(response)`, `WithField` pour une réponse à plusieurs formes, `errorMessage` et `invalidPaths` pour un refus (`tests/integration/api.ts`). Lancement : `npm run build && TEST_DATABASE_URL=postgresql://…/limbus_test npm run test:integration`. En local sous Windows, il faut passer par un conteneur Linux.

Bout en bout : Playwright (`tests/e2e/`), dans Chromium, contre l'application compilée et la même base de test : connexion, déconnexion, 403, accès au compte (mot de passe oublié, inscription libre, confirmation, changement d'adresse et de mot de passe, export et effacement), écriture du jeu (création, renommage, suppression de chaque élément, partage d'un jeu), page publique, legs, inscription sur invitation, actions de l'équipe sur les inscriptions, compte, administration, participants, présence, et les parcours (casting, trombinoscopes, envoi des documents, paiements, hors ligne, modification, annulation et report d'une session, présence, timeline de session, qualité du questionnaire), assistants d’IA (page « Autoriser », assistants connectés, réglage du partage), nouveautés. Les parcours partagent le « Jeu des parcours » préparé par `globalSetup.ts` ; chaque test y crée sa session (`parcoursSession`) et ouvre la session par cookie (`signIn`), car l'écran de connexion limite à 10 tentatives par email (ADR-0037). Les fichiers de tests tournent sur trois navigateurs en parallèle, avec un seul faux serveur d'emails (ADR-0059) : un test lit ses emails par `openMailbox` et les adresse à une personne qui lui est propre (`parcoursPerson`), et ne change aucun réglage global. Lancement : `npm run build && TEST_DATABASE_URL=… npm run test:e2e`. Sous Windows, passer par l'image `mcr.microsoft.com/playwright:v<version>-noble` (même version que `@playwright/test`). Attendre `networkidle` avant de remplir un formulaire : avant l'hydratation, le clic le soumet nativement.

Dépendances : Dependabot ouvre chaque lundi une PR groupée (mineures et correctifs) et une PR par version majeure. La CI les valide ; les fusionner les déploie.

Unitaires : Vitest (`tests/`). `tests/setup.ts` recrée les auto-imports Nitro (`createError`, `getHeader`, `useRuntimeConfig`…) et remplace Prisma par un objet vide. Dans un test, on lui assigne les méthodes nécessaires (voir `tests/server/auth.test.ts`). `h3` est fixé en v1 en devDependency pour correspondre à Nitro.
